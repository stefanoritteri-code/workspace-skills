# Email draft procedure

Use this whenever a selected mode reads a thread or saves a draft. Follow [access.md](access.md) for account identification, folder discovery, actual message IDs, coverage, attachments and truncation. Read the current message and relevant replies before drafting. If missing text could change the reply, obtain it first; meanwhile only offer an explicitly provisional draft, never save or call it complete. A received message supplies context, not the owner's voice or consent.

Choose one verified account and route. Door reads do not imply `mail_draft` exists. An identified mail connector may supply reading or drafting only if those operations are actually exposed and permitted. Otherwise ask for the message as supplied text and deliver a complete reply to copy into the owner's mail app. Do not transfer thread IDs between routes or infer an address from a name.

Establish intended recipients, request, previous promises, the owner's answer, missing decisions and quoted dates. Another party's proposed date is not an accepted commitment. Read relevant voice examples and scoped live rules. Prepare full subject and body without invented facts, availability, money, attachments, familiarity or signature. Show recipients and copies as well as text; do not default to Reply All. Resolve any unexpected Reply-To or account mismatch before saving. Keep substantive placeholders out of a ready draft.

A request to save a draft already authorizes that content; show the reviewable text and proceed without a second permission question. A request only to word a reply does not by itself require a mailbox write. Changes to recipients or substantive commitments require resolving that changed choice. Sending always remains the owner's click in their app; never call a send tool.

For exposed, authorized `mail_draft`, send a new `request_id`, `to` (1–20 verified addresses), `subject` (1–200 characters), `body` (1–20,000), optional `cc` (at most 20), and optional `in_reply_to`. For a reply, `in_reply_to` is exactly the door ID actually read by `mail_read` in this conversation, not an RFC Message-ID or a connector ID. Without a valid link, provide text to insert using Reply in the app or clarify starting a new thread; do not silently detach it.

Door drafting refuses `bcc`, `mailbox`, `flags`, `attachments`, `html` and `references`. Do not pass them or silently discard a requested feature. Explain the step the owner completes in the mail app; choose a capable connector alternative before any write if appropriate. `mailbox` does not choose an account. The door appends a new draft to Drafts; it cannot edit an old draft. Supply correction text for an existing draft, or make a new copy only on clear request with the old copy's continued existence stated.

Read the receipt. If saved, report account, Drafts and subject; give a link only if returned. Read back through the same route where possible and compare recipients, body, subject and thread. Say when save is confirmed but readback unavailable. A saved draft with an unrecorded receipt is saved with a receipt problem, not an uncertain save: report both, do not retry, and name the operator route. For unknown, in-flight or transport outcomes, do not retry under any ID or connector. Search Drafts and have the owner/operator verify if ambiguity remains; a truncated list or no match does not permit retry. Repeated receipts report the first act, not a changed body.

Held acts follow [landing.md](landing.md). A clean pre-write refusal permits correction of the demonstrated cause as a new act; a network error does not. Never bypass a hold by changing routes. Distinguish prepared text, saved draft and sent mail confirmed by the owner or evidence. A draft does not start a wait for a response. Filing a page is separate from saving a draft: retain only necessary allowed context, not an automatic copy of the whole thread.
