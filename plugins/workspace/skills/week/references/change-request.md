# What should change

Use this mode when the owner says «l'istruzione dovrebbe dire… / the instruction should say…» or «mi servirebbe una skill per… / I need a skill for…». It can start on any day without a weekly review. A request proposes a maintained change; it does not adopt a new governing rule.

Read the project's instruction for the named operator and permitted scope. Retrieve any existing request on the same topic through [access.md](access.md). Keep the requested change, reason and one concrete example in the owner's own words. Reuse what they have already said; ask only for a missing reason, example or formulation, without inventing their case. If they are only exploring an idea, offer to keep it; an explicit request to file it is already consent.

Follow [landing.md](landing.md) to write a page titled `Request — <the owner's requested change>`, translated to the project's language. Keep the owner's wording within the title limit; ask for a shorter formulation if needed. The body contains their exact request, reason and example, with word-first headings. Use `author: owner` only for those actual words. Check the canonical path before creation; append to the existing same-topic request rather than duplicate it. Do not record the proposed instruction as a live decision or create an implementation deadline. A separate chosen follow-up needs its own agreed date and does not promise delivery.

Read the receipt and saved page back, then tell the owner in plain language: “Your request is saved here: <confirmed page>. <operator named in the project's instruction> reads these requests, decides what to change and makes the change. I do not edit my own instruction or skills. Saving this request does not notify the operator or mean the change has been made.” In Italian: «La tua richiesta è salvata qui: <pagina confermata>. <operatore nominato nell’istruzione del progetto> legge queste richieste, decide cosa cambiare e fa la modifica. Io non modifico la mia istruzione né le mie skill. Salvare la richiesta non avvisa l’operatore e non vuol dire che la modifica sia stata fatta.» Never promise a date or imply automatic delivery, monitoring or implementation. If the operator is not named or reachable by a stated route, say that the handoff remains unresolved; ask for the operator route without inventing a person or sending a message.

Explain these two lines to the owner when discussing maintenance:

- You can change your own project's instruction text yourself; it then diverges from the maintained version, so the operator must reconcile your edits before later maintained updates can be applied consistently.
- You cannot change a skill's file, the door's rules or a standing decision yourself through this room; request the change from the operator named in your project's instruction.

In Italian:

- «Puoi cambiare tu stesso il testo dell’istruzione del tuo progetto; da quel momento si discosta dalla versione mantenuta, e l’operatore deve riconciliare le tue modifiche prima che gli aggiornamenti successivi si possano applicare in modo coerente.»
- «Non puoi cambiare da questa stanza il file di una skill, le regole della porta o una decisione permanente; chiedi la modifica all’operatore nominato nell’istruzione del tuo progetto.»

For held, refused, partial or uncertain writes, use the landing recovery procedure and report that state instead of saying the request is saved. The system never edits its own instruction or skill files, even if the owner phrases the request as “update yourself”.
